Money & Influence

Everything here is disclosed, and has been for years. It is disclosed across 2,073 lodger names and both sides of every gift, which is why nobody reads it. This puts it back together.

The size of it

What the family disclosed in the window, and how many hands it came from.

Who funds it

One row per donor per year, every branch collapsed into a single figure — the number that appears on no individual return. Select a donor to drill in.

Money that reached several arms of the same party

Donors whose giving spanned three or more separate legal entities of this family.

Who these donors are

The register names a legal lodger. This asks what public sources say that name is — each statement attributed, each source graded by what kind of evidence it is.

How it works

The data

The figures come from the AEC Transparency Register's annual disclosure returns, held in this realm's own provisioned PostgreSQL store (datasource au_donations, loaded by scripts/load-aec.py). The appliance reads it read-only through governed sql producers that generate their own SELECTs: familyBackersByFamily (table family_backers, behind FamilyBacker), sameDayByDonor (same_day_multi_party, behind SameDayGiving) and donorIdentityByName (donor_identity, behind DonorIdentity). Political families are this realm's own mapping (sql/party_families.sql), not the AEC's; the family list in the selector is families.json, shipped beside this page.

How fresh: the AEC releases annual returns on the first business day of February, and the store holds whatever the loader last loaded — re-running the loader is what refreshes it. Each producer caches its reads for a day.

“Who these donors are” and the drill-in's sources are the only parts that leave the store. They read DonorTrailHit through webForPhraseRead, which calls the webSearch operation (Brave web search, declared by the companion realm-gov-au) for the donor's name and then reads the top three pages, keeping bounded excerpts around the name. Those results are cached for six hours. The paragraph in the dossier is written by a model, once per donor, from the register line and those excerpts only.

The questions

The page calls seven views of this realm, each by name through POST /api/v1/views/{name}/invoke. This is the Cypher each one runs.

PartyFundingScale — The size of it: how many donors disclosed to the family since the chosen year, the total, the number of gifts, and how many of the family's legal entities the widest-spread donor reached. Parameters: familyName, sinceFy.
MATCH (f:PartyFamilyQuery {name: $familyName})-[:HAS_BACKER]->(b:FamilyBacker)
WHERE b.financial_year >= $sinceFy
RETURN count(DISTINCT b.donor_name) AS donors,
       sum(b.total)                 AS disclosedTotal,
       sum(b.gifts)                 AS gifts,
       max(b.branches)              AS mostEntitiesOneDonorReached
FamilyBackers — Who funds it: one row per donor per financial year, every lodging branch of the family summed into one figure, largest first. Parameters: familyName, sinceFy, limit (the “Donors to show” control).
MATCH (f:PartyFamilyQuery {name: $familyName})-[:HAS_BACKER]->(b:FamilyBacker)
WHERE b.financial_year >= $sinceFy
RETURN b.donor_name      AS donor,
       b.financial_year  AS financialYear,
       b.total           AS total,
       b.gifts           AS gifts,
       b.branches        AS branches,
       b.branches_lodged AS branchesLodged,
       b.tiers           AS tiers
ORDER BY b.total DESC
LIMIT $limit
BranchSpreading — Money that reached several arms: donors whose gifts reached at least three separate legal entities of the family, most entities first. Parameters: familyName, sinceFy, minBranches = 3, limit = 8.
MATCH (f:PartyFamilyQuery {name: $familyName})-[:HAS_BACKER]->(b:FamilyBacker)
WHERE b.financial_year >= $sinceFy AND b.branches >= $minBranches
RETURN b.donor_name      AS donor,
       b.financial_year  AS financialYear,
       b.branches        AS branches,
       b.total           AS total,
       b.branches_lodged AS branchesLodged
ORDER BY b.branches DESC, b.total DESC
LIMIT $limit
PartyFundingDossier — Who these donors are: for the largest donors (at most five), web pages that mention the donor are searched and read, ranked by kind of source, and a model writes one short paragraph per donor from those pages and the register line only. Parameters: familyName, sinceFy, limit = the smaller of “Donors to show” and 5.
MATCH (f:PartyFamilyQuery {name: $familyName})-[:HAS_BACKER]->(b:FamilyBacker)
WHERE b.financial_year >= $sinceFy
WITH b ORDER BY b.total DESC, b.donor_name, b.financial_year LIMIT $limit
// A PERSON is lodged surname-first ('Wall, Pamela') — a string no article, filing or profile
// carries — so a search under the lodged form finds nothing and the largest donor in a report
// comes back blank. Inverted for the SEARCH only; every printed name stays as lodged.
WITH b,
     CASE WHEN b.donor_name CONTAINS ', ' AND NOT b.donor_name =~ '(?i).*(pty|ltd|limited|council|union|association|group|holdings|trust|inc).*'
       THEN trim(split(b.donor_name, ',')[1]) + ' ' + trim(split(b.donor_name, ',')[0])
       ELSE b.donor_name
     END AS searchName
OPTIONAL MATCH (c:CoverageQuery {phrase: searchName})-[:HAS_READ_RESULT]->(h:DonorTrailHit)
// Directories, aggregators and social pages restate an address and a like-count. They identify
// nobody, and every one of them displaces a source that does.
WHERE h.url IS NULL OR NOT h.url =~ '(?i).*(linkedin|facebook|twitter|instagram|dnb|creditorwatch|companiesdb|opengovau|australialei|bloomberg|aus61business|ib\.com\.au|rightsindevelopment|claytonutz|donation\.watch).*'
// ONE ROW PER DONOR, ITS FIRST THREE SOURCES, each labelled with WHAT KIND it is. A row per
// SOURCE let one well-covered donor consume the whole brief while three others went unmentioned:
// coverage cannot be requested in a prompt when the input itself is lopsided. Grouped here,
// every donor is exactly one item, so a brief that drops one is visibly short.
//
// The kind is folded into the collected map rather than projected in its own WITH, and nothing
// orders on a fetched property — after a paid per-anchor hop both defeat the planner, and the
// failure surfaces as an unrelated "unknown function" rather than as a refusal.
// EVIDENCE GRADE DECIDES WHAT A READER SEES FIRST. A substantial-holder notice lodged under law
// and a company profile page arrive from a search engine in popularity order, which is not the
// order that helps anyone weigh a claim about who funds a political party. Ranked here, so the
// three sources kept per donor are the three strongest available rather than the three most
// popular. (This was believed impossible for several days: ordering on a fetched property
// appeared to be refused by the planner. It was not — see embabel/me#871.)
WITH b, searchName, h,
     CASE
       WHEN h.url =~ '(?i).*(asx|asic|abr)\\.(com|gov)\\.au.*' THEN 1
       WHEN h.url =~ '(?i).*\\.gov\\.au.*'                     THEN 2
       WHEN h.url =~ '(?i).*wikipedia\\.org.*'                 THEN 4
       ELSE 3
     END AS grade
ORDER BY b.total DESC, b.donor_name, grade
WITH b, searchName,
     collect(CASE WHEN h.url IS NULL THEN null ELSE {
       kind: CASE
         WHEN h.url =~ '(?i).*(asx|asic|abr)\\.(com|gov)\\.au.*' THEN 'a disclosure lodged under law'
         WHEN h.url =~ '(?i).*\\.gov\\.au.*'                     THEN 'a government register'
         WHEN h.url =~ '(?i).*wikipedia\\.org.*'                 THEN 'an encyclopaedia entry'
         ELSE 'reporting by a named publication'
       END,
       title: h.title,
       url: h.url,
       // BOUNDED QUOTE. The producer reads a 3,000-character window per page; three of those
       // per donor is more than one composition call can hold, and the fold then summarises
       // its own partials — which silently drops whole donors from the brief. 400 characters
       // carries the sentence that identifies the donor, which is all this needs.
       text: left(replace(replace(coalesce(h.content, h.snippet, ''), '<strong>', ''), '</strong>', ''), 700)
     } END)[0..3] AS srcs
WITH b.donor_name AS donorAsLodged, searchName AS searchedAs, b.total AS total, srcs,
     b.donor_name + ' disclosed $' + toString(b.total) + ' to ' + $familyName + ' in ' +
     b.financial_year + ', in ' + toString(b.gifts) + ' gifts' +
     CASE WHEN b.branches > 1
       THEN ' across ' + toString(b.branches) + ' separate party entities (' + b.branches_lodged + ')'
       ELSE ''
     END + '.' +
     CASE WHEN size(srcs) = 0 THEN ' No published source was found.'
       ELSE reduce(acc = '', s IN srcs |
         acc + ' SOURCE, ' + s.kind + ' — ' + s.title + ' <' + s.url + '>: ' + s.text)
     END AS line
// ONE ROW PER DONOR, AND ONE COMPOSITION PER DONOR. Neo4j groups an aggregation by the other
// returned keys, so returning the donor beside `render(...)` finalises the reduction once per
// donor rather than once per report.
//
// That is not a performance choice, it is a correctness one. Composing eight donors in a single
// pass drifts: four consecutive runs each introduced a word no source used — "wholly" for
// "100%", "violations" for "infringement notice", and once "ties" between a donor and the
// party, which is the unsupported relation this realm exists to refuse. Five donors passed
// first time. The variable is how much a model must hold at once, so this holds one donor.
//
// Coverage also stops being something to check: N donors in, N rows out, and a missing donor is
// a missing ROW that any caller can count — not a silently shorter paragraph.
RETURN donorAsLodged AS donor,
       searchedAs    AS searchedAs,
       total         AS disclosedTotal,
       render(line,
         'Report this donor: the register facts, then at most two sentences on who it is according to its SOURCE lines, naming the source and what kind it is. Prefer what identifies the donor — who owns or benefits from it — over anything else a source discusses. Never assert a connection yourself; a source says it, in its own words. Do not write that anything is associated with, linked to, related to or behind anything else unless a source says exactly that. Where there is no source, say so in a clause.'
       ) AS prose,
       head(collect(srcs)) AS sources,
  'These are amounts disclosed under law. They say nothing about what any donor sought or received. Gifts below the disclosure threshold do not appear. Donor and recipient returns are separate disclosures that need not agree. Statements about who a donor is are quoted from the named source, not asserted by this realm — a filing and a news report are different kinds of evidence, and both may be dated. The register asserts only the name on the return.' AS caveats
ORDER BY disclosedTotal DESC, donor
DonorIdentity — Drill-in, spellings: every spelling the donor lodged under (same ABN, or identical after normalising case, punctuation and legal suffix) and the combined total. Parameters: entityName = the donor as lodged.
MATCH (q:DonationQuery {name: $entityName})-[:HAS_IDENTITY]->(i:DonorIdentity)
RETURN i.canonical_name      AS canonicalName,
       i.variants            AS variants,
       i.variant_names       AS variantNames,
       i.combined_total      AS combinedTotal,
       i.combined_gifts      AS combinedGifts,
       i.this_spelling_total AS thisSpellingTotal,
       i.identity_key        AS identityKey
SameDayGiving — Drill-in, same-day giving: dates on which this donor paid more than one political family, up to six. Parameters: entityName = the donor as lodged, limit = 6.
MATCH (q:DonationQuery {name: $entityName})-[:HAS_ENTITY]->(e:DonationEntity)
MATCH (e)-[:PAID_MANY_ON_A_DAY]->(s:SameDayGiving)
RETURN toString(s.made_on)  AS madeOn,
       s.financial_year     AS financialYear,
       s.families_paid      AS familiesPaid,
       s.paid_that_day      AS paidThatDay,
       s.which_families     AS whichFamilies
ORDER BY s.families_paid DESC, s.paid_that_day DESC
LIMIT $limit
PartyFundingSources — Drill-in, sources: the pages the dossier read, with the text actually read from each; the page keeps only the rows for the selected donor. Parameters: familyName, sinceFy, limit.
MATCH (f:PartyFamilyQuery {name: $familyName})-[:HAS_BACKER]->(b:FamilyBacker)
WHERE b.financial_year >= $sinceFy
WITH b ORDER BY b.total DESC, b.donor_name, b.financial_year LIMIT $limit
WITH b,
     CASE WHEN b.donor_name CONTAINS ', ' AND NOT b.donor_name =~ '(?i).*(pty|ltd|limited|council|union|association|group|holdings|trust|inc).*'
       THEN trim(split(b.donor_name, ',')[1]) + ' ' + trim(split(b.donor_name, ',')[0])
       ELSE b.donor_name
     END AS searchName
OPTIONAL MATCH (c:CoverageQuery {phrase: searchName})-[:HAS_READ_RESULT]->(h:DonorTrailHit)
WHERE h.url IS NULL OR NOT h.url =~ '(?i).*(linkedin|facebook|twitter|instagram|dnb|creditorwatch|companiesdb|opengovau|australialei|bloomberg|aus61business|ib\.com\.au|rightsindevelopment|claytonutz|donation\.watch).*'
RETURN b.donor_name      AS donorAsLodged,
       searchName        AS searchedAs,
       b.total           AS disclosedTotal,
       b.financial_year  AS financialYear,
       b.gifts           AS gifts,
       b.branches        AS branches,
       b.branches_lodged AS branchesLodged,
       CASE
         WHEN h.url =~ '(?i).*(asx|asic|abr)\\.(com|gov)\\.au.*' THEN 'a disclosure lodged under law'
         WHEN h.url =~ '(?i).*\\.gov\\.au.*'                     THEN 'a government register'
         WHEN h.url =~ '(?i).*wikipedia\\.org.*'                 THEN 'an encyclopaedia entry'
         WHEN h.url IS NULL                                     THEN null
         ELSE 'reporting by a named publication'
       END AS sourceKind,
       h.title      AS title,
       h.url        AS url,
       replace(replace(coalesce(h.content, h.snippet, ''), '<strong>', ''), '</strong>', '') AS text
ORDER BY disclosedTotal DESC, donorAsLodged, url

When it looks wrong

“No disclosures for … since …” means the store holds no disclosed gift to that family in the window. It is an answer, not an outage: try an earlier financial year. Gifts below the disclosure threshold never appear. “No donor reached three or more separate entities” is likewise an answer for that family and window.

A box headed “The data could not be fully fetched” means a producer returned rows with a warning — most often the web search or a page read in the dossier. The rows shown are real, but incomplete; it is never shown as an empty answer. “Could not read this” means the view call itself failed, timed out after three minutes, or your session lapsed; reload, or sign in again.

In the drill-in, a missing spellings or same-day block means that view returned no rows for this donor, and “nothing further was resolved” means none of the three did. A donor with no sources in the dossier had no page found under its name (people are searched forename-first, though printed as lodged). The dossier is the slow panel: it searches and reads pages on first use, then serves from cache.

Donor names are not merged across spellings in the tables; the drill-in's spellings block shows the combined figure.

What made this possible

The page has no backend of its own: it asks the appliance for views by name, and every sum, rollup and ranking is done in the view's Cypher, so the page recomputes nothing. A relational table (family_backers) is read as graph nodes by a declared sql producer — no copy of the database is made. The dossier joins those rows to live web pages in the same query: OPTIONAL MATCH (c:CoverageQuery {phrase: searchName}) triggers the search and page reads for exactly the donors the query selected, and render(...) composes one paragraph per donor inside that query, so a missing donor is a missing row.

Every figure is read live from this realm's views — PartyFundingScale, FamilyBackers, BranchSpreading, PartyFundingDossier, DonorIdentity, SameDayGiving and PartyFundingSources — and nothing on this page is recomputed from them.

Family labels are ours, from the realm's committed mapping, not the AEC's: the register names legal lodgers, and rolling divisions of one party together is a defensible analytical act rather than a fact the Commission asserts. Every rollup shows the entities it spans so it can be taken apart again. A disclosure is a sourced fact, never a finding.
